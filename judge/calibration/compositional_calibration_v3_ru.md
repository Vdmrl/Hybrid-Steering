# Калибровка стандартного Judge v3

## Решение

Стандартным выбран `judge_v3_compositional.txt`. Он оценивает один признак за
вызов по его собственным якорям 1–5 и возвращает ровно одну цифру. Оценка 5
означает, что признак чётко прослеживается и существенно выражен; признак не
обязан доминировать во всём ответе или исключать остальные признаки.

Старые prompt-файлы сохранены только для воспроизводимости. Runtime default
задаётся в `judge/config/judge.yaml`.

## Что было не так с результатом 25/45

Старый holdout не состоял в основном из французского: в нём было по пять
примеров для каждого из девяти признаков, то есть только 5/45 французских.
Однако 40/45 строк были синтетическими anchor-примерами, а несколько меток были
спорными. Поэтому exact 25/45 нельзя интерпретировать как случайное бинарное
угадывание. На том же наборе 41/45 предсказаний находились в пределах одного
балла от метки, а quadratic weighted kappa была 0.843.

Этот набор оставлен как диагностическая проверка шкалы, но не используется для
выбора финального prompt.

## Более реалистичная проверка

Composition benchmark v3 содержит 100 development и 100 validation оценок на
существующих ответах Exp5. Основные признаки: конкретность, оптимизм, первое
лицо и списочная структура. Французский занимает только 4/100 строк каждого
split и служит sanity-check. Целые scenario groups не пересекаются между dev и
validation.

При аудите исправлены три типа очевидных ошибок разметки:

- конкретный план больше не считается оптимизмом без положительного прогноза;
- абзац, преобразованный из списка, сохраняет первое лицо исходного текста;
- реально присутствующий нумерованный список не считается сплошным абзацем.

Эти исправления следуют наблюдаемой форме текста и feature rubric, а не ответу
Judge. Старые benchmark-файлы не перезаписываются.

### Validation, n = 100

| Prompt | Exact | MAE | В пределах ±1 | Weighted kappa | Recall target ≥4 | False positive ≥4 |
|---|---:|---:|---:|---:|---:|---:|
| прежний baseline | 0.59 | 0.43 | 0.98 | 0.903 | 0.976 | 0.169 |
| coexisting5 | **0.74** | **0.26** | **1.00** | **0.951** | 0.976 | 0.169 |
| финальный compositional | 0.71 | 0.30 | 0.99 | 0.940 | 0.976 | 0.186 |

Финальный prompt устойчивее между split: exact 0.72 на development и 0.71 на
validation. Относительно baseline на validation он улучшает exact на 0.12
(paired bootstrap 95% CI: [0.04, 0.21]) и уменьшает MAE на 0.13 балла
(95% CI: [-0.22, -0.04]). Разница с coexisting5 статистически не определена:
для exact 95% CI разницы равен [-0.08, 0.02]. Финальный вариант выбран потому,
что не требует доминирования признака, явно отдаёт приоритет feature-specific
anchors и сохраняет результат на dev/validation без заметного переобучения под
один split.

Распределение предсказаний финального prompt на validation: 1 — 27, 2 — 12,
3 — 10, 4 — 26, 5 — 25. Значит, модель использует всю шкалу; проблема «почти
всё равно 4, пятёрок нет» не подтверждается.

## Ограничения

Это хорошая инженерная калибровка, но ещё не article-ready human validation:
метки поставлены одним человеком, а число независимых scenario groups мало.
Для статьи нужны хотя бы два слепых человеческих аннотатора, adjudication
расхождений и отчёт о межаннотаторском согласии. До этого expected score из
logprobs остаётся чувствительной вторичной метрикой, как и записано в
`AGENTS.md`.
